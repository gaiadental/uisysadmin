# Audit 001: konfirmasi aksi krusial (2026-10-12)

Mode: after. Tidak ada file kode yang diubah. Daftar ini menunggu nomor yang disetujui.

Cakupan: semua aksi destruktif di aplikasi. Ada 11 titik konfirmasi, semuanya lewat satu komponen (`components/dialogs/dialogs.tsx`).

| Aksi | Lokasi | Bisa dibatalkan? |
|------|--------|------------------|
| Hapus akun user | `team/users/use-user-actions.ts` | Tidak |
| Hapus peran | `team/roles/use-role-actions.ts` | Tidak |
| Hapus permission | `catalog/master-permissions/permission-list-page.tsx` | Tidak (memengaruhi pemetaan tenant dan peran) |
| Hapus negara | `catalog/countries/country-list-page.tsx` | Tidak (kode tidak bisa dipakai lagi) |
| Hapus kategori tenant | `catalog/tenant-categories/tenant-category-list-page.tsx` | Tidak |
| Nonaktifkan tenant | `tenants/detail/tenant-detail-page.tsx` | Ya |
| Tangguhkan, nonaktifkan user | `team/users/use-user-actions.ts` | Ya |
| Paksa keluar user | `team/users/user-sessions-tab.tsx` | Sebagian (user masuk lagi) |
| Reset password user | `team/users/use-user-actions.ts` | Tidak (password lama hilang) |

Catatan aturan: antislop tidak punya aturan khusus untuk konfirmasi destruktif. Temuan ini memakai C-4 (resilience: UI tahan terhadap kesalahan pengguna) dan C-1 (setiap keputusan punya alasan).

## Temuan

Prioritas: HIGH, MEDIUM, LOW.

1. **HIGH, semua aksi diperlakukan sama.** Hapus permanen dan nonaktifkan yang bisa dibalik memakai dialog yang sama: satu klik pada tombol merah. Tidak ada tingkatan menurut dampak. (C-4)
2. **HIGH, hapus permanen hanya butuh satu klik.** Hapus user, peran, permission, negara, dan kategori selesai dengan satu klik di dialog. Satu klik salah di baris, lalu satu klik salah di dialog, sudah menghapus data. (C-4)
3. **HIGH, tombol Hapus menempel di tombol Ubah.** Di tiap baris tabel, tombol merah Hapus berjarak 6px dari Ubah, dengan ukuran sama. Salah klik sangat mungkin. Contoh: `team/roles/role-action-buttons.tsx`. (C-4)
4. **MEDIUM, fokus awal dialog tidak ditentukan.** `DialogContent` tidak mengatur fokus awal. Fokus bisa jatuh ke tombol konfirmasi, sehingga Enter atau Spasi yang tidak disengaja menghapus data. Perlu diverifikasi di browser. (R-32, C-4)
5. **MEDIUM, dampak tidak disebut konkret.** Teks seperti "Pemetaan ke tenant dan peran ikut terpengaruh" tidak menyebut jumlahnya. Hapus peran tidak menyebut berapa user yang memakainya. Pengguna tidak bisa menimbang risiko. (C-1)
6. **MEDIUM, nonaktifkan tenant lewat switch.** Satu geseran switch membuka dialog yang tombol merahnya sama ringannya. Dialog tidak menyebut berapa user tenant yang kehilangan akses. (C-4)
7. **LOW, tombol konfirmasi dan Batal sama bobotnya.** Tombol hapus sama besar dan sejajar dengan Batal, dan posisinya di kanan (posisi yang biasanya dipakai untuk aksi aman). (C-4)
8. **LOW, tidak ada jeda atau tahan-untuk-konfirmasi.** Tidak ada penghalang gerak refleks.

## Konflik dengan arsitektur yang sudah disetujui

ARCH-FE-001 D11 dan REQ-FE-039 menetapkan dialog konfirmasi destruktif tanpa input ketik ("with no typed input"). Dialog konfirmasi ketik nama tenant bahkan sengaja dihapus (D7 dan daftar UPDATE `dialogs`). Konfirmasi dengan mengetik hanya boleh diterapkan lewat perubahan arsitektur dan ADR baru melalui `decision-manager`. Temuan 1 sampai 8 di bawah ini dirancang agar tidak memerlukan input ketik.

## Usulan perbaikan (menunggu persetujuan nomor)

Tiga tingkat, tanpa input ketik:

- **Tingkat 1, bisa dibalik** (nonaktifkan, tangguhkan, paksa keluar, reset password): dialog tetap satu langkah. Fokus awal di **Batal**, tombol aksi tidak berfokus. Dampak konkret ditampilkan.
- **Tingkat 2, hapus permanen** (user, peran, permission, negara, kategori): dialog dua langkah. Fokus awal di Batal. Tombol hapus nonaktif sampai pengguna mencentang "Saya mengerti ini permanen dan tidak bisa dibatalkan", lalu ditahan 1,5 detik (tombol terisi merah bertahap) untuk mengeksekusi. Ada ringkasan apa yang hilang.
- **Tombol di baris:** Hapus dipindah dari baris ke menu "Lainnya" (tiga titik) atau ke bagian "Zona berbahaya" di halaman detail. Tombol Ubah tetap di baris.

Pembukaan tahan-untuk-konfirmasi dan checkbox adalah penghalang gerak refleks, bukan input teks, jadi tetap sesuai D11.

Pilih nomor temuan yang akan diperbaiki. Nomor yang tidak disebut tidak disentuh.

## Hasil perbaikan (disetujui: semua temuan, 1 sampai 8)

| # | Status | Perubahan |
|---|--------|-----------|
| 1 | Selesai | Dialog punya dua tingkat: `permanent` (hapus) dan biasa (bisa dibalik). |
| 2 | Selesai (diubah) | Hapus permanen butuh mengetik "delete" di kolom dialog sebelum tombol merah aktif. Versi awal (centang dan tahan 1,5 detik) diganti atas permintaan pemilik. |
| 3 | Selesai | Hapus di baris menjadi tombol ikon pendiam di balik pembatas (`delete-button.tsx`), berjarak dari Ubah. Dipakai di role, user, permission, negara, kategori. |
| 4 | Selesai | Fokus awal dialog di Batal (terverifikasi test). |
| 5 | Sebagian | Dampak konkret ditulis sebagai daftar (`impact`). Angka (jumlah user per peran, dll.) tidak ada di kontrak API, jadi tidak ditampilkan. |
| 6 | Sebagian | Dialog nonaktifkan tenant mendapat fokus awal di Batal dan tombol Batal menonjol. Jumlah user tenant tidak tersedia dari API. |
| 7 | Selesai | Batal jadi tombol utama (teal) di kanan, tombol destruktif di kiri. |
| 8 | Selesai (diubah) | Penghalang refleks kini berupa kata yang harus diketik, bukan penahanan. |

Catatan arsitektur: konfirmasi ketik bertentangan dengan ARCH-FE-001 D11 ("with no typed input"). Pemilik memutuskan memakainya. D11 dan REQ-FE-039 perlu diperbarui lewat `decision-manager` (ADR baru).
